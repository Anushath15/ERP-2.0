# Failure modes

Columns: what goes wrong, what the shop sees, how the app prevents or survives it, and the test that proves it. Status: **Proven** (a test already passes), **Planned** (test written in Phase 2/3), **Not verifiable here** (needs real hardware).

| # | Cause | Effect on the shop | Prevention / survival | Proving test | Status |
|---|---|---|---|---|---|
| 1 | App crash or force-kill mid-save | A half-saved bill | Saving a bill is one SQLite transaction (bill, lines, movements, ledger, payment, outbox). All or nothing. The draft is autosaved every few seconds and restored on next start | Crash-at-every-step test: throw after each statement, reopen, assert no partial bill and draft present | Planned (P3) |
| 2 | Power cut mid-transaction | Same | SQLite WAL + `synchronous=FULL`. Kill the process during writes in a loop, reopen, run `integrity_check`, compare totals | Power-cut simulation (kill -9 loop) | Planned (P3) |
| 3 | Disk full | Save fails | Check free space at start and before save (warn under 500 MB); a failed transaction rolls back; friendly message "Not enough space. Your last bill was NOT saved. Free some space and press Save again"; the draft stays on screen | Fill a small volume, save, assert rollback and message | Planned (P3) |
| 4 | Database file corrupted | App will not open or shows wrong data | `quick_check` at start (0.3 s for a 116 MB db, S2); on failure auto-restore the newest backup that passes `integrity_check`, tell the owner in plain words, keep the bad file aside | Corrupt a copy by overwriting bytes, start, assert restore | Planned (P3) |
| 5 | System clock wrong or changed (forward / back) | Bills dated wrongly, edit conflicts | Bill date is user-visible and editable with warning; ordering uses the hybrid clock and sequence numbers, not the clock; cursors use server time; after each sync the clock is compared with server time and a warning shows when 5+ minutes off | S4-4 (clock two days ahead: converges, warning raised) | **Proven** (sync part) |
| 6 | Firebase down or slow | No sync | Everything works locally; backoff with jitter; status shows "Offline - saved on this PC" | S4-3 (down, 5,000 changes, reconnect: 5,000 writes, no loss) | **Proven** |
| 7 | Internet drops mid-sync | Partial upload | Atomic commits; unacked rows stay in the outbox; re-sent safely | S4-1 (15% dropped requests) | **Proven** |
| 8 | Duplicate, reordered, partial delivery | Double bills or lost rows | Idempotent UUIDv7 ids; rules accept an identical re-send; pull applies append-only records with insert-if-missing | S4-1: lost replies re-delivered 3,100 writes for 2,500 records, both devices equal, no invoice number twice | **Proven** |
| 9 | Two devices edit the same record | Lost edit | Last writer wins on hybrid clock; loser kept in history and shown in audit view | S4-4 | **Proven** |
| 10 | Two devices bill at once | Same invoice number | Per-device invoice series (prefix per device) generated inside the save transaction | S4-5 (600 bills from 2 devices, all numbers unique, both devices equal) | **Proven** |
| 11 | Quota exhausted | Cloud rejects requests | In-app guard pauses at 70%; local work continues; no billing account exists so nothing can be charged | Guard unit tests with fake counters | Planned (P2) |
| 12 | Auth token expired while offline | Locked out | The app never blocks on token refresh; once signed in stays signed in; refresh only when online; only a server-side revoke seen while online signs out | Offline-start test with expired token | Planned (P2) |
| 13 | Failed schema migration | App will not open | Automatic backup before migration; migration runs in a transaction on a copy first; on failure restore the backup and say so | Migration rollback test | Planned (P3) |
| 14 | Failed app update | Old/new mix | Updates are manual in v2.0 (copy of folder / installer); data lives outside the app folder; new version refuses to open a newer database | Version-gate test | Planned (P3) |
| 15 | Poisoned record that will not sync | Stuck queue | Bisection isolates it, it goes to "Needs attention" with plain-words help; others continue | S4-2 (1 bad of 500: 499 delivered) | **Proven** |
| 16 | Very large data (50,000 bills, 5,000 products, 10,000 customers) | Slow screens | Paged lists, FTS5 search, indexes, cached stock/balance totals that can be rebuilt | S2: search p95 1.3-2.2 ms, list page p95 45 ms, save p95 20 ms at 50,000 bills (Windows). Report queries need caching (see S2 finding) | **Proven** (Windows); mobile Not verified |
| 17 | Memory growth over an 8-hour day | Slowdown | Streams closed, lists windowed, no unbounded caches; soak test | 8-hour simulated soak with memory sampling | Planned (P3) |
| 18 | Printer missing / offline | Cannot print | Bill is saved first; print is a separate retryable step; "Print again" in the sales register; save as PDF fallback | Printer-offline integration test | Planned (P2); real printer Not verified |
| 19 | Lost or stolen device | Someone can see data | Optional app-lock PIN; owner revokes the device (writes blocked), "Sign out everywhere"; see threat-model | Rules test: revoked device cannot write | **Proven** (write block) |
| 20 | Operator double-clicks Save | Two bills | Idempotency key per save: unique index on `idem_key`; Save button disables while saving | Unit test: same key twice = one bill | Planned (P2) |
| 21 | Unexpected UI exception | Crash or stack trace | Global error handler: log locally without personal data, friendly message, draft kept | Widget test that throws in a child | Planned (P2) |
| 22 | Backup file bad or missing | Cannot restore | Backup verified by reading it back (open + `integrity_check` + row counts); keep 30; copy before migration/restore | Backup verify test | Planned (P2) |
| 23 | Another person's data requested | Data leak | Rules deny all but members; tested for cross-shop reads | S1 rules tests (other shop read/write, unverified email, id mismatch, oversize, unknown collection) | **Proven** |
| 24 | Windows permissions / antivirus locks DB file | Cannot save | Database in the user's data folder, retry-with-message, never in the install folder | Manual on shop PC | Not verified |
| 25 | Name typed with unusual letters | Odd characters on a printout | The software is English only. Fonts cover Latin letters, digits, the rupee sign and common punctuation; other text is stored and shown as typed, and may print with the system fallback | Test: the rupee sign and punctuation print correctly | Planned |

## Added 2026-10-13
| # | Cause | Effect | Prevention / survival | Test | Status |
|---|---|---|---|---|---|
| 26 | Two devices create bills, purchases, adjustments, opening stock offline and sync in any order, with lost, duplicated and delayed deliveries | Different stock or balances on each device | Stock and balances are derived only from synced records; append-only records are inserted if missing and never altered | `s4_convergence_test.dart` (3 seeds) | **Proven** |
| 27 | **Stolen or lost signed-in device** | The thief can read shop data for up to about **1 hour** (a Firebase sign-in token stays valid until it expires; there is no server to cancel it without paid Functions) | Owner ends the device quickly: (1) change the account password (all refresh tokens end; the device is locked out within the hour); (2) remove the person's e-mail from the allowed list in the rules and redeploy (rules design b) or from the Staff screen (design a), which blocks the account at once for reads and writes; (3) design (a) only: mark the device revoked to block its writes immediately. An optional app-lock PIN protects the screen meanwhile | Rules tests: unlisted e-mail denied (allowlist test), revoked device cannot write (S1) | **Proven** (rules); 1-hour read window is a documented limit |

| 31 | Bill cancelled after part payments | Wrong balance | The bill's credit is reversed by one entry; later payments become an advance; reversal happens once | `credit_test`, `credit_flow_test` | **Proven** |
| 32 | WhatsApp not installed, no internet, wrong or missing number | Reminder cannot open | Button disabled with the reason when offline; number asked for and validated; app link falls back to wa.me; if opening fails nothing is counted and "Copy message" is offered | `reminder_test`, `credit_screens_test` | **Proven** (our logic); real WhatsApp Not verified |
